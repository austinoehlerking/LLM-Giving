# Volunteer startup and launch contract

The Standard preset sets a sixty-minute/three-assignment limit. It does not select a model, effort, provider or tool. Unknown settings remain unknown. Under the existing platform planning policy they cannot qualify for planning, and requester-specific model/effort/mode requirements can exclude later work too. Unrestricted non-planning research may still qualify. Never make every empty queue an authorization error or manufacture a model setting.

The review page shows a read-only availability preview before authorization. Its Worker settings action opens an editable configuration/recheck form; it changes the proposed configuration only, leaving the legal and resource consent boxes unchecked. Supply settings for the actual research worker, not just the browser controller. Planning options are read from the current server policy. Rechecking cannot claim, renew, release, submit, generate a handoff/snapshot, accept terms or change an existing session. A stored session keeps its captured settings/consent; use a new authorization to change them.

src/volunteer-startup.php enumerates only approved public current-round tasks and applies scope, profile, requester requirements, the canonical worker matcher, current reservation/prerequisite/visibility gates and contributor lineage. Reasons distinguish missing planning settings, requester mismatch, profile/tool consent, reservations (with public expiry), prerequisites, holds and completed work. Public task links and requirements can explain a mismatch. Pending/private/withdrawn topics and quarantined bodies are never enumerated or counted; a pending-only scope simply has no published work. At most300 task rows are inspected, prioritizing Ready tasks; a truncated preview explicitly says it is partial and recommends a narrower scope. A preview is advisory; all original transactional pickup and recording checks remain authoritative.

The private dashboard repeats current availability. An empty pickup now reports an actionable reason instead of only a generic mismatch. No queue diagnosis acquires a lease, adopts an existing reservation, advances a task or broadens scope. Existing active assignments direct the controller back to their own reservation controls. No polling, automatic approval or administrative operation is introduced.

The authorization receipt copies a first-person launch request followed by the COMPLETE unchanged public reference and actual private session supplement. vo_launch_request composes this only through vo_handoff's current access, state and credential checks. The volunteer reviews and sends it as their own direct message. A reference-only attachment, website permission statement or embedded secret alone does not grant an AI runtime human tool permission. Runtime approvals remain in force; copying sends nothing and guarantees neither tool access nor model provenance. The sequential session controller may continue within live limits; each individual research worker stops after its assignment. Private capabilities never enter public instructions, research packets, context, archives or screenshots.

No migration or historical snapshot rewrite is needed. Existing session settings/consent, task signatures, resource/legal checks, independent review, reservation lifecycle, receipt recovery and actual worker evidence remain unchanged. The separate compact-authorization change owns not-collected human-declaration semantics; this feature does not recreate removed declaration/profile UI or turn missing declarations into none.

Focused checks: php tests/volunteer-startup.php, php tests/volunteer-orchestrator.php and php tests/volunteer-queue.php. node tools/qa.mjs orchestrator includes the startup UI test: unknown Standard, truthful worker recheck, complete launch copy, cross-browser transfer, actual local synthetic pickup/Check/Submit/receipt recovery, required first viewports and enlarged text. These generated research packets are explicitly synthetic software tests, not genuine AI research or paid/native-worker launches. Real user-session diagnosis and external runtime acceptance must be reported separately; no live credential or session is needed for these local fixtures.
