# Volunteer startup and launch contract

Quick try defaults to 15 minutes or one task. Volunteers choose what their AI can do and how much time to give. For in-depth research or independent review, use Extra High, Max, or your AI’s equivalent if available. Model and reasoning can still be reported in completed packets when available.

The review page shows a read-only availability preview before authorization. Its Availability details action shows the eligibility reasons and lets a volunteer review a different capability profile. Rechecking changes the proposed configuration only. It cannot claim, renew, release, submit, generate a handoff or snapshot, accept terms, or change an existing session.

src/volunteer-startup.php enumerates only approved public current-round tasks and applies scope, task capabilities, software consent, current reservation/prerequisite/visibility gates and contributor lineage. Reasons distinguish capability and software-consent gaps, reservations (with public expiry), prerequisites, holds and completed work. Public task links and requirements can explain a mismatch. Pending/private/withdrawn topics and quarantined bodies are never enumerated or counted; a pending-only scope simply has no published work. At most300 task rows are inspected, prioritizing Ready tasks; a truncated preview explicitly says it is partial and recommends a narrower scope. A preview is advisory; all original transactional pickup and recording checks remain authoritative.

The private dashboard repeats current availability. An empty pickup now reports an actionable reason instead of only a generic mismatch. No queue diagnosis acquires a lease, adopts an existing reservation, advances a task or broadens scope. Existing active assignments direct the controller back to their own reservation controls. No polling, automatic approval or administrative operation is introduced.

The authorization receipt copies a first-person launch request followed by the COMPLETE unchanged public reference and actual private session supplement. vo_handoff is the single canonical launch payload: it validates current access, state and the exact private credential before composing the direct user request, complete public reference and private supplement. A separate wizard/copy surface must copy these bytes rather than reconstructing or forking the payload. The volunteer reviews and sends it as their own direct message. A reference-only attachment, website permission statement or embedded secret alone does not grant an AI runtime human tool permission. Runtime approvals remain in force; copying sends nothing and guarantees neither tool access nor model provenance. The sequential session controller may continue within live limits; each individual research worker stops after its assignment. Private capabilities never enter public instructions, research packets, context, archives or screenshots.

No migration or historical snapshot rewrite is needed. Existing session settings/consent, task signatures, resource/legal checks, independent review, reservation lifecycle, receipt recovery and actual worker evidence remain unchanged. The separate compact-authorization change owns not-collected human-declaration semantics; this feature does not recreate removed declaration/profile UI or turn missing declarations into none.

Focused checks: php tests/volunteer-startup.php, php tests/volunteer-orchestrator.php and php tests/volunteer-queue.php. node tools/qa.mjs orchestrator includes the startup UI test: capability-only Quick try, truthful capability recheck, complete launch copy, cross-browser transfer, actual local synthetic pickup/Check/Submit/receipt recovery, required first viewports and enlarged text. These generated research packets are explicitly synthetic software tests, not genuine AI research or paid/native-worker launches. Real user-session diagnosis and external runtime acceptance must be reported separately; no live credential or session is needed for these local fixtures.
